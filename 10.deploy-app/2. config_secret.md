# ConfigMap & Secret Guide

How configuration and sensitive values are loaded into the express app pods.

> **Current setup uses Kustomize** (`kubectl apply -k k8s/`).
> The Secret is generated from `k8s/.env` at apply time — the file never
> leaves your machine or reaches GitHub.

---

## 1. The big picture

| Object | Stores | Example keys | Managed by | Source |
|---|---|---|---|---|
| **ConfigMap** | Non-sensitive config | `NODE_ENV`, `LOG_LEVEL`, `APP_PORT` | `k8s/configmap.yaml` (committed) | declarative YAML |
| **Secret** | Sensitive values (passwords, API keys, tokens) | `APP_NAME`, `API_KEY`, `DB_PASSWORD` | `secretGenerator` in `k8s/kustomization.yml` | `k8s/.env` (gitignored) |

Config flow:

```text
k8s/.env
  │  read locally at apply time (NOT committed to git)
  ▼
secretGenerator (kustomization.yml)
  │  creates Secret "express-env-<hash>"
  ▼
Deployment: envFrom.secretRef ──▶ Pod ──▶ process.env.*

k8s/configmap.yaml (committed to git)
  ▼
kubectl apply -k k8s/
  │  creates ConfigMap "express-config"
  ▼
Deployment: envFrom.configMapRef ──▶ Pod ──▶ process.env.*
```

---

## 2. Where does `express-env` come from?

It is **generated by Kustomize** — there is no `secret.yaml` in the repo.

`k8s/kustomization.yml`:

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - configmap.yaml
  - deployment.yaml
  - service.yaml
secretGenerator:
  - name: express-env
    envs:
      - .env # file inside k8s/, gitignored
```

Apply everything with:

```bash
kubectl apply -k k8s/ # -k = kustomize, not -f
```

What happens at apply time:

1. Kustomize reads `k8s/.env` **locally** (security load-restrictor: it
   only reads files inside the kustomization directory — so `.env` must
   live in `k8s/`, not the project root)
2. Every `KEY=VALUE` line becomes a key in the Secret
3. The Secret is created as `express-env-<hash>` — the hash is derived
   from the **content** (currently `express-env-td62ft4g92`)
4. Kustomize rewrites the deployment's `secretRef: name: express-env`
   to the hash-suffixed name automatically

**Why the hash matters:** when `.env` changes, the hash changes → new
Secret name → pod template changes → **automatic rolling restart**.
No manual `kubectl rollout restart` needed for secret updates anymore.

> **Gotcha:** referencing `../.env` (outside the kustomize folder) fails
> with `evalsymlink failure ... lstat` — kustomize refuses to load files
> outside its own directory tree. Keep `.env` inside `k8s/`.

View a generated secret value:

```bash
kubectl get secret -l app=express            # find the hash-suffixed name
kubectl get secret express-env-td62ft4g92 -o jsonpath='{.data.APP_NAME}' | base64 -d
```

## 3. Where does `express-config` come from?

Plain declarative YAML, committed to git at `k8s/configmap.yaml`:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: express-config
data:
  NODE_ENV: production
  LOG_LEVEL: info
  APP_NAME: express
  APP_PORT: "4010"
```

Why different strategies?

- Config is not sensitive → safe to commit → reproducible in CI/CD
- Secrets must never be committed → generated locally from `.env`,
  which is gitignored

> **Alternative:** Kustomize also has `configMapGenerator` (same hash +
> auto-restart behavior as `secretGenerator`). Consider it if you want
> config changes to trigger rollouts too.

## 4. How pods consume them

In `k8s/deployment.yaml`:

```yaml
envFrom:
  - configMapRef:
      name: express-config # ALL its keys become env vars
  - secretRef:
      name: express-env # rewritten by kustomize to express-env-<hash>
```

`envFrom` injects **every key** from the referenced object as an
environment variable. The app reads them normally in Node:

```js
process.env.LOG_LEVEL // "info"
process.env.APP_PORT  // "4010"
```

### Precedence (who wins if a key exists in multiple places)

```text
1. env: (explicit entry in pod spec)   ← highest
2. Secret (via secretRef)
3. ConfigMap (via configMapRef)        ← lowest
```

Use an explicit `env:` entry to override one key without touching the
ConfigMap/Secret.

---

## 5. Reload behavior

| What changed | Pods pick it up |
|---|---|
| `.env` (via secretGenerator) | **automatically** — hash changes, rollout happens on next `kubectl apply -k k8s/` |
| `configmap.yaml` (plain resource) | **NOT automatically** — env vars are injected only at container start. Run `kubectl rollout restart deploy express-deploy` after applying |

## 6. Day-to-day commands

```bash
# Apply everything (config + secret + deployment + service)
kubectl apply -k k8s/

# Change non-sensitive config → edit k8s/configmap.yaml, then:
kubectl apply -k k8s/
kubectl rollout restart deploy express-deploy

# Change secrets → edit k8s/.env, then:
kubectl apply -k k8s/          # rollout is automatic (new hash)

# Verify what the pods actually see
kubectl exec deploy/express-deploy -- printenv | grep -E 'APP_|NODE_ENV|LOG_LEVEL'

# Inspect the objects
kubectl get configmap express-config -o yaml
kubectl get secrets                           # look for express-env-<hash>

# Preview what kustomize will build (without touching the cluster)
kubectl kustomize k8s/                        # or: kubectl apply -k k8s/ --dry-run=client -o yaml
```

## 7. Repo hygiene (IMPORTANT before pushing to GitHub)

```bash
# .gitignore must contain:
k8s/.env
.env
```

Optionally commit a `k8s/.env.example` template listing the required
keys (without values) so others know what to configure:

```env
APP_NAME=express
API_KEY=your-secret-here
DB_PASSWORD=your-secret-here
```

If you previously created the Secret manually
(`kubectl create secret generic express-env ...`), it's now unused —
kustomize manages `express-env-<hash>` instead:

```bash
kubectl delete secret express-env
```

---

## 8. Production checklist

- [x] Config in declarative YAML, committed to git
- [x] Secrets generated from `.env`, never committed (`k8s/.env` gitignored)
- [x] Kustomize `secretGenerator` → content-hash suffix → auto-rollout on change
- [ ] Commit `k8s/.env.example` as a template
- [ ] Enable `immutable: true` on ConfigMaps that never change
      (delete + recreate to change, then rollout restart)
- [ ] At team scale, move to **overlays** (`k8s/overlays/dev|staging|prod`)
      with per-environment config
- [ ] For sensitive values in CI/CD, use encrypted-in-git approaches
      (**SOPS + age**, **Sealed Secrets**) or external managers
      (External Secrets Operator, Vault) — plain `.env` generation only
      works where the CI runner can be trusted with the file
